## 1. 目标与决定来源

首先把现有 V20 星空体验接入作者的真实 Hexo 博客，在 Netlify 验证上线；随后另建开源仓库，提供可复制整个项目、修改配置后建站的完整模板。

个人博客保留旧 Kira 版本及星空版本，支持作者恢复旧版发布。公开模板只承载通用星空实现、配置示例、示例文章和可再分发的通用素材。

依据：[本次访谈 Q1–Q18](theme-discovery.md)、[原设计及后续反馈](../../docs/design/starry-blog.md)、[V20 原型记录](../../themes/hexo-theme-kira/prototypes/starfield/README.md)。用户已确认 Q17 理解准确，整体方案和 R1–R6 范围调整后规则暂无调整，见第 8 节。

## 2. 建议技术栈与职责

| 部分 | 建议实现 | 目的与边界 |
| --- | --- | --- |
| 内容与页面生成 | 现有 Hexo 与 Markdown 渲染管线 | 保留写作方式、原文章格式和真实永久链接；构建时生成正文和集合页。 |
| 正式主题 | 独立的 `themes/hexo-theme-starry/`，使用项目已有 EJS 渲染能力 | 名称为工作名；旧 Kira 目录及配置保留。 |
| 星空交互 | 原生 JavaScript ES modules、Canvas 2D、当前 WebGL 投影及 CSS | 保留当前视觉与互动目标，按职责抽取原型代码。 |
| 内容索引 | 构建时生成轻量文章元数据与正文入口 | 首页只加载必要索引；正文按文章进入，避免一开始把所有长文和播放器载入。 |
| 可编辑配置 | YAML；工具生成的数据使用带版本字段的 JSON | 内容/关系与通用主题实现分开；星位与场景校准结果随仓库保存。 |
| 本地工具 | Node.js 提供本地场景校准界面及发布准备命令 | 桌面和手机插画分别校准，导出配置；无需管理账户。 |
| 发布 | 现有 GitHub → Netlify → `public/` | 继续静态托管；不需要在线写作后台、数据库或访客端 AI。 |

以上是基于已确认需求的工程建议，不代表这些文件或命令已经存在。准确依赖版本以实现阶段实际安装与干净构建结果固定。本仓库已有 npm 和 pnpm 两份锁文件；建议以当前 Netlify npm 流程为基线，先确认锁文件及旧版构建，再固定 npm，避免把依赖升级和清理混入主题迁移。

只读核对已确认：`package-lock.json` 锁定 Hexo 8.1.2，`pnpm-lock.yaml` 锁定 8.0.0；本机为 Node 22.19.0/npm 10.9.3，仓库没有固定 Node 版本。这些是本地事实，不代表 Netlify 的实际环境。

## 3. 项目边界与配置

建议正式化后的组织：

```text
themes/
  hexo-theme-kira/             旧版主题和已有原型证据保留
  hexo-theme-starry/           正式星空主题（工作名）
    layout/                   HTML 与 EJS 模板
    scripts/                  Hexo 数据适配、资源与路由生成
    source/                   正式 JS、CSS、通用组件资源
    tools/                    本地校准与发布准备工具
source/
  _posts/                     现有文章
  _data/
    starry-relations.yml      双向语义关系和作者采用的理由
    starry-layout.json        固定文章身份对应的关联模式星位
    starry-scenes.json        桌面/手机图片、区域、遮罩和镜头参数
  image/                      个人素材
_config.yml                   站点与当前主题选择
_config.hexo-theme-kira.yml    原 Kira 配置
_config.hexo-theme-starry.yml  星空外观、内容入口和体验选项
```

文件名为建议；实现时确认后统一写入使用文档。原型 URL 参数中的美术对照、历史版本、mock 增长、调试工具与状态查看器保留为开发证据，不作为公开主题默认界面。

使用者日常修改的范围：站点与作者信息、文章与引言、友链、已采用的文章关系、字体/配色/星光/云层/动画参数，以及桌面和手机场景素材。生成的配置须有可定位的检查提示和版本字段；新增可选项应有兼容默认值。

## 4. 正文、身份、星位与写作流程

### 内容加载和静态可读

每个原文章地址生成含真实标题、摘要、正文、规范地址和分享信息的 HTML。先以正文可阅读为基础，星空、数据与界面准备成功后才切入完整体验；脚本禁用、资源加载失败或 WebGL 不可用时保持正文可达，不能只靠 `noscript` 应付脚本运行失败。

星空中的阅读层使用同一份 Hexo 渲染内容。进入另一篇文章时，根据真实正文入口加载内容并更新地址；直接打开和刷新该地址同样正常。链接本身是可导航的真实地址，历史状态与内容层同步，避免使用统一 SPA 回退把所有路径都改成首页。

静态标题/摘要服务于搜索引擎与分享，不构成新增站内搜索功能。首版不新增 RSS、正文目录、评论或其他 Q10 列出的功能；原正文中的既有代码块、HTML、图片和音乐仍属于兼容工作。

### 固定身份和位置

固定身份独立于显示标题、文件名、数组序号和 Hexo 缓存 ID。首次导入现有文章时补齐身份并记录实际原地址；更名、改日期、同日发表、补发旧文、删除和恢复文章都应有验证案例。

关联模式读取已提交的星位分配。新文章在保留已有坐标的基础上分配位置，参考作者已采用的关系并保持留白。若之后补充远距离关系，也保持旧星坐标，通过连接和导航表达关系。没有关系的文章仍可发表并出现。

时间模式按日期与固定身份稳定排序；补发旧日期文章可以改变时间序列中的落点，关联模式已有位置保持不变。两种模式共享文章身份。

双向关系只配置一次；自动邻近导航线与语义关系分别存储、解释和渲染，邻近路线不产生虚构关联理由。AI 仅按需辅助作者准备候选，作者采用的结果才进入公开数据。

### 作者发布流程

1. 继续在本地 Markdown 写文章，可选填引言及关系。
2. 本地准备步骤自动补身份、分配新星位并校验内容/配置；尽量接入已有本地构建体验。
3. 本地预览后，把文章、身份和生成的配置一起提交并推送。
4. Netlify 检查已提交数据并生成静态站点，不把 CI 中临时生成且未提交的位置当作下一次增长的依据。

准备命令必须可重复运行：相同输入不移动已有星位，不重复创建身份。全新内容缺少必要布局时，构建给出明确的准备步骤提示；按已确认 R4，失效可选关系给定位提示并跳过，有效文章仍可访问。

## 5. 本地插画校准与性能

本地校准工具载入桌面/手机图片，可分别标记窗口通透区与入口、描画遮罩、定位互动区域及设置穿窗镜头参考。坐标采用图片内相对位置，导出后用于不同尺寸和裁剪方式；提供首屏、手机与穿窗/返回的预览，保存与取消行为清楚。先导出文件，再由作者放入仓库，避免默默覆盖图片或正式配置。

作者介绍入口已确认首版暂缓；工具结构允许后续配置书桌物件的跳转目的地，不提前制作新介绍页或新增首页介绍入口。

低性能模式优先减少装饰星、云层细节、微动和渲染分辨率，保留核心探索、穿窗和阅读。减少动态偏好与性能降级分开处理。WebGL 不可用时有可读路径；具体低配阈值通过实际前台与真机采样确定，不预设或宣称已达到某个帧率。

## 6. 地址、Netlify 和旧版恢复

路由任务以真实构建产物建立完整清单，包含文章、归档年月及分页、标签、分类、独立页面、中文编码、站点根路径及正文锚点。

- 首页：当前窗边入口与默认关联模式。
- 文章：原地址对应静态正文及同篇文章的星空阅读层。
- 归档：对应星历盘/日期范围，保留所指年月和分页范围。
- 标签与分类：星空中的对应文章集合清单，首页不增加常驻菜单。
- 友链：对应友链信号内容。
- 旧关于：按 Q17 保留原内容及歌单的轻量兼容承接，首版不制作新介绍入口。

Netlify 延续静态输出；具体构建命令是否加校验步骤在实现时确认，并继续使用 `public/` 作为正式发布目录。核对实际生产分支、Node 版本、包管理器安装、base directory、部署上下文与资源缓存。新主题先在独立预览环境验证；当前原型服务限制本地运行，不能作为生产服务。

旧版恢复必须形成具体可执行步骤：记录旧部署与源代码/配置版本，保留旧主题资源、所需插件及配置，验证切回旧配置能够重新生成并发布旧布局。平台恢复已有部署可作为快速手段，长期恢复能力以保存的源代码、配置与依赖为依据。

原型和旧主题文件保留；正式实现通过新目录与配置承载，正式切换以前不改变当前线上主题。旧主题的布局、脚本和个人素材不自动带入未来公开模板。

主题目录隔离不足以保证渲染隔离：现有 Kira npm 依赖引入的 `hexo-kira-toc` 包含全局正文 filter，可能改写新主题的标题锚点；需要检查实际影响，必要时限定适用主题或隔离构建配置。播放器兼容也有三种来源：正文 `meting` 标签、文章 `subheading` 中的 `<meting-js>`、旧归档页的 `meting` 元信息。已安装插件和 Kira 主题均注册过 `meting`，实现中明确适用注册与资源加载，不能假设旧脚本会自动跟随新主题。

旧页独有歌单的承接以 Q17 为准；正文内现有音乐按内容兼容要求处理。当前没有使用的 Kira 自定义标签不自动扩展为首版必做能力。

## 7. 实施阶段和完成标准

| 阶段 | 交付 | 结束条件 |
| --- | --- | --- |
| 0. 基线与边界 | 当前工作保存、旧版构建与地址/内容清单、新主题骨架、依赖/运行时记录 | 旧版可重建，工作区改动可追溯，新旧构建互不覆盖验收证据。 |
| 1. 第一条真实文章链路 | 新主题生成一篇真实文章；同址静态正文、星空进入阅读、直接打开/刷新和历史返回 | 从生成到阅读完整跑通；禁用脚本及模拟加载失败仍能读文；旧布局仍能构建。 |
| 2. 全量内容与稳定星图 | 10 篇现有文章、身份/星位准备、双向关系、双模式、引言与媒体适配 | 新增孤立文章可发表，既有星位不变，改名/补发/恢复可定位，真实内容不丢失。 |
| 3. 场景配置与本地校准 | 外观配置、桌面/手机图与互动区域导出、预览与穿窗校准 | 换一套不同构图素材，只修改素材和配置即可完成入口及过渡。 |
| 4. 兼容入口与设备 | 归档/友链、旧标签分类清单、完整路由映射、触屏与低性能处理 | 旧链接对应正确内容；目标设备可探索和阅读；关于入口按最终决定验收。 |
| 5. 个人站点发布 | Netlify 预览、内容复核、正式切换与恢复记录、使用说明 | 托管环境实测通过，切回旧版路径验证，未验证设备/性能项明确记载。 |
| 6. 独立公开模板 | 通用内容/素材、独立仓库、干净安装与配置教程 | 新使用者从空环境复制模板、改配置和示例文章后能构建部署，包内没有个人内容和旧版主题。 |

第 1 阶段优先验证真实文章整条链路，而不是先把全部原型代码搬过去再检查内容。公开模板整理虽在个人站点上线后进行，配置与通用实现的分离从阶段 0 开始。

实现验证覆盖身份和星位不变、同址静态正文/脚本失败、旧地址直达与历史、真实图片及音乐、校准文件导入、触屏关键动作、干净 Netlify 构建和旧版恢复。视觉参数通过画面对照与真实设备体验校准，测试不只复制实现公式。原型已有视口测试不等于触屏真机或正式站点性能验收。

## 8. 整体复核结果

Q17：用户确认理解准确。首版暂缓新作者介绍及首页介绍入口；旧 `/pages/mine/` 保留现有内容及歌单的轻量兼容承接。未来书桌物件跳转介绍暂不实施。

Q18：用户确认整体方案和规则暂无调整。[原设计第 9 节 R1–R6](../../docs/design/starry-blog.md)已按本次范围更新为确认状态，承载刷新/浏览器返回、时间模式理由、移动中断、引言与异常关系、功能入口反馈和正文音乐规则。此处仅记录产品要求确认，不表示验收通过。

已确认的范围调整：R5 沿用现有原型小交互，不新增原稿中尚未制作的两项趣味彩蛋；R6 原正文音乐兼容保留，旧关于承接按 Q17 处理，其他旧页独有音乐不自动成为新版全站功能，作者介绍的书桌跳转作为后续候选。

本方案已综合为 [正式规格](spec.md)，准确源文件名仍由实现时确定；后续按规格拆票和实施，避免本记录与规格独立漂移。旧版恢复、公开模板仓库边界与 Netlify 的已确认要求不再重新询问。
