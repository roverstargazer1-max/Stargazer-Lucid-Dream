日期：2026-10-01。

状态：本地主题实施、静态构建与代码复核已完成。当前进展和验证证据见 [implementation-progress.md](implementation-progress.md)。按本轮要求未 push；实际托管部署和真实触屏验收保留为发布前事项，默认生产主题仍为 Kira。

## 目标

将作者确认的最终窗边星空体验接入当前全部真实文章，作为个人 Hexo 博客发布。旧版的文章、图片、Kira 本地主题、配置及必要依赖完整保留，并提供可验证的切回方式。

首版使用当前全部真实文章验收。体验范围包括窗边入场和返回、半球巡视与缩放、互动云、星图与方位操作、关联/时间模式、点星靠近与简介、纸面正文、文末关联、阅读返回与停靠历史、现有小彩蛋和轻过渡。具体动画、美术和布局以作者最后体验并认可的 V20 为准。

调试面板、模拟文章增长、布局导出、历史美术与 A/B 切换留在开发原型。公开发行、后台、AI 推荐、场景校准工具和大规模模拟验证不作为本次首版交付目标。

继续使用现有 Hexo、EJS、Markdown 渲染、原生 JavaScript、Canvas 及当前厚涂背景的原生 WebGL。独立正式主题承载新页面和交互，Kira 与原型保留。

补查发现 codex/prototype-starfield 已有独立 themes/stargazer-starfield、真实文章链路、稳定布局和双向关联等部分实现。实施的第一步是将其与本次要求逐项核对，优先复用符合要求的模块；不把整条分支的旧需求自动并入新范围。

当前 dev 原型为 V13，codex/prototype-starfield 原型为 V20。作者已明确以 V20 为基准，包括连续穿窗、反向归窗、书页开合和窄屏操作优化。

素材基准已核对该分支实际入口：桌面 room-poster-detail-v20.png 与 room-window-mask-v17.svg；手机 room-portrait-v11.png 与 room-window-portrait-mask-v17.svg。正式主题现有配置的桌面 room-personal-v20.png 应对齐此最终原型。

## 作者可编辑的数据

建议把关联放在文章 Front-matter 的 related 字段。支持直接写文件名，以及附理由的写法；下面只是格式提案，不是实际文章内容：

```yaml
related:
  - 另一篇文章的文件名
  - post: 第三篇文章的文件名
    reason: 两篇文章之间的关联理由
```

- 引用 source/_posts 中的文件名，不带 .md，不用标题作为标识。当前全部文件名唯一。
- 每对文章只需要配置一次，自动生成双向关系；没有理由时仍可打开对方文章。
- 不根据标签或空间邻近生成语义关系。探索路径与内容关联分别生成和展示。
- 实现时检查自关联、失效目标与重复条目，给出包含源文章的定位提示。未知目标不应造成合法文章不可阅读。
- 如果已有内部稳定身份机制可复用，文件名先解析到身份；作者不需要手动维护编号。
- 所有现有文章自动进入星空，未填关联也可发布。星等默认普通，重要/珍藏及孤立属性提供可选配置，字段名称由实现统一说明。
- 星位持久保存并随仓库提交；新增文章只分配新位置。时间模式按真实发布日期排序，其序列不承担关联模式旧星不移动的约束。

## 正文、地址和旧入口

保留现有文章 URL 规则及已经分享的文章地址。每个文章地址生成可直接阅读的 HTML，关闭阅读后进入对应文章的星空；星空阅读和直达阅读使用同一份真实正文。

实际内容使用标题、列表、引用、加粗、链接、相对图片路径及原生 HTML/style，不能只沿用 mock 的纯文本 p 元素。已有音乐涉及文章元信息和旧独立页面，需核对相应脚本及资源。文章内的样式需要控制作用范围。

现有 /pages/archive/、/pages/friends/、/pages/mine/，以及生成的归档、标签和分类路由，在新版保留原链接和内容，并提供最小兼容承接：文章集合链接显示所指集合，独立页面保留已有正文、友链数据和实际音乐内容。首页保持 V20 原型界面，不增加常驻归档、友链或介绍菜单。

验收时逐条检查现有路由、年月及分页范围、中文路径与内容对应关系，避免把不同旧地址统一指向首页而丢失原内容。

已读、镜头与停靠状态按最终原型在当前访问期间保存；跨次记忆未列入本次已确认需求。原型已有的尊重减少动态设置及轻过渡体验按最终版本核对。

## 发布准备与稳定布局

旧星保持位置需要可复现的布局来源，不能仅依赖访客浏览器状态或托管构建缓存。另一个分支已有本地 prepare:starfield 命令，保存生成的数据后随文章一起推送。

作者已确认将准备步骤接入本地预览：写 Markdown → 执行一次预览，自动准备并保存新星位 → 提交文章和布局 → 推送 GitHub → Netlify 生成静态文件。托管端读取已提交数据，遇到新增文章缺少准备结果时给出清楚提示。

实施时把现有 prepare 与 preview 包装成作者只需执行一次的入口，并在日常使用文档说明应一并提交的文件。预览会自动完成数据准备，不要求作者另行手填身份或坐标。

## Netlify 兼容判断

架构判断：兼容现有 GitHub 推送后自动构建并发布静态目录的方式。正式主题生成 HTML/CSS/JS/图片与文章数据，访客的探索和阅读在浏览器完成，原型的本地开发服务不作为生产服务。

当前仓库的 netlify.toml 使用 npm run netlify，发布 public；新主题的 .preview 目录仅用于本地验证。切换时应沿用正式发布目录或同步更新平台配置，不能把预览目录误作为线上成果。

必须核对：实际生产分支、安装方式、Node/npm 版本、base directory、构建命令、发布目录与部署上下文。当前有 npm/pnpm 两套锁文件；选择 npm 流程后要核对并固定适合新旧主题的环境。Netlify 配置文件中的同名设置优先于 UI 设置，但部分绑定与部署信息仍需平台实测。

检查实际 Linux 构建对中文路径与大小写的处理、文章深链接刷新、相对图片和 ES module 资源路径、带缓存资源的版本更新，以及新旧配置的恢复。按每篇文章生成静态页面，不依赖统一 SPA 首页回退解决所有地址。

当前在线 GitHub 默认分支确认为 master，当前 dev 没有 upstream；不能以此推定 Netlify 绑定分支。只读状态接口没有返回部署检查，也不能证明线上成功或失败。本轮未执行构建、访问 Netlify 管理页或部署，因此兼容结论是方案可行性，不是已通过线上验收。

## 实施入口和交付标准

从 codex/prototype-starfield 的正式主题成果开始逐项核对与修正，保留当前文档和旧版基线。把本次要求与旧分支计划的差异明确写入后续任务，避免继续执行公开模板、校准工具和额外规模验证等超出此次范围的旧任务。

第一批具体调整是：对齐 V20 桌面素材；支持文章 related 字段和文件名引用；恢复无理由关联在文末的入口；把预览与准备统一成一次操作。随后补齐星等/孤立配置、性能自动降级和尚未承接的旧页面，按上述阶段验收。

最终交付包含可预览的独立主题、已接入的全部真实文章、简明文章配置说明、一次预览后推送的写作流程、原链接兼容清单、托管预览结果及旧版切回步骤。现有模块的代码存在不等于完成交付；每项以本次实际验证结果判定。
